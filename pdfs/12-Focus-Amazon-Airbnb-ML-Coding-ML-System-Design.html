01. Amazon L5 Applied Scientist: ML Coding Round

Scope: the coding round(s) in the Amazon L5 Applied Scientist (Applied Scientist II) phone screen and onsite loop, with the focus on ML coding: implementing algorithms, losses, metrics, sampling and data pipelines from scratch in Python, NumPy or PyTorch. A short DSA section at the end covers the LeetCode-style problems reported in AS loops. This chapter merges and dedupes four independent search passes with the earlier chapters amazon-l5-applied-scientist/chapters/05-ml-coding.md and 04-coding-dsa.md. Questions only. No answers or solutions.

Tags: [Reported] means a candidate report, or an aggregator of candidate reports, ties the coding task to an Amazon science loop (citation [n]). Where the report is from a junior, intern, Senior, Data Scientist, Research Scientist or MLE loop, the line says so. [Likely] means the task is inferred: the concept was asked verbally in a breadth or depth round, or the prompt comes from a practice site or prep guide and no candidate report says it was coded. Many Glassdoor sources were read only as search-result extracts, and several extracts could not be tied to one exact review ID; the reference list flags these. Treat each report as the candidate's account.

Ordering: within each section, questions are ordered by how many independent reports name them, then by importance for an L5 loop. Numbering runs across the whole chapter.

How this round works

  • Where it sits. Amazon's AS prep page describes the onsite as 55-minute interviews with scientists [1]. AS II candidates in 2025-2026 report five rounds: ML breadth, ML depth, team-specific system design, coding, and a Bar Raiser [6]. A 2026 loop was "1 phone screen, 1 coding, 2 ML design and 2 LP rounds" [23]. A London 2026 loop had live coding plus ML depth and breadth rounds, 60 minutes each [32]. L5 phone screens mix ML concepts, statistics, LPs and a short coding task [9][74].
  • What the coding task looks like. It depends on who interviews you [73]. An SDE-style interviewer gives "leetcode at L4 SWE bar. Correctness is top priority, explain your answer, give complexities" [17]. A scientist interviewer "tends to ask ML questions such as PCA and least squares" [11]; Blind commenters call OLS, gradient descent and batch normalization fair game, but not bagging, boosting or a vanilla recommender [10][14]. Reported mixes: "two coding questions, one ML related and the other an easy to medium leetcode question" (Melbourne, Nov 2025) [23]; "two easy Leetcode problems, some ML coding problems" (Santa Monica AS II, 2026) [3]; an ML coding round separate from ML design and LP rounds in a two-day onsite [51]; "most questions were non-leetcode questions more related to day to day ml implementations" (2026) [23]. LLM teams ask decoding code (beam search) in the screen [8]; AGI teams report debugging a broken Transformer, training a small classifier live, and RL coding [56].
  • Duration and pacing. 45 to 60 minutes [28][32]. LP questions often take the first 20 to 30 minutes, and several reports describe only about 15 minutes left for code [53][54][70]. Practice each core primitive so it fits in 15 minutes.
  • Language and tools. Python. NumPy for from-scratch numerics, PyTorch on deep-learning and LLM teams, and no scikit-learn estimators unless the task is a dataset round, where pandas, NumPy and sklearn are allowed [13]. You write in Amazon's shared editor (Livecode), with no IDE, and the code is usually not run, so you trace it by hand [1][2][71]. Amazon asks for syntactically correct code, not pseudo code [2]; a Berlin candidate who wrote k-means in "a mix of Python and pseudo-code" shows how this gets tested [7].
  • What is evaluated at L5. Correct, readable, vectorized code; complexity stated without prompting; edge cases (empty input, ties, a single class, all-zero weights) raised before you are asked; numerical stability (max-subtraction, log-space, stable variance); and an answer to the scale-up follow-up (streaming, mini-batch, distributed) [17][53][54]. Preparation matters: an LLM-team candidate could not deliver working beam search "as I hadn't prepared" [8], while a Senior AS candidate passed with an unfinished graph problem by narrating the approach clearly [49].

A. Classical ML from scratch

  1. k-means. Implement kmeans(X: np.ndarray, k: int, max_iters: int = 300, tol: float = 1e-4, init: str = "k-means++", seed: int | None = None) -> tuple[np.ndarray, np.ndarray] returning centroids (k, d) and labels (n,). Alternate assignment and update steps, stop when the centroid shift is below tol or at max_iters. Handle: empty clusters, k > n, duplicate points, k = 1. No sklearn. [Reported] [7][15][39][52] (Berlin AS, Feb 2025, coded in Python [7]; a 2024 phone screen and a distance-metric follow-up [39]; Amazon aggregator sighting Dec 2025 [52]; also on Amazon-tagged practice lists [58][69])

    • What is the cost per iteration, and can you compute all point-to-centroid distances with broadcasting and no Python loop over points?
    • Can you implement k-means++ seeding as its own function, and why does it help?
    • What do you do when a cluster goes empty?
    • Which distance metric would you use, and what goes wrong when features have very different dynamic ranges (price vs rating)? [39]
    • How would you choose k?
    • How would you run it on data that arrives as a generator of (b, d) batches, or on 1 billion product embeddings (mini-batch, distributed)?
    • How would you port it to PyTorch tensors on a GPU? [68]
    • Does it always converge, and to what?

  2. Logistic regression / "a traditional ML classifier" from scratch. Implement class LogisticRegression with fit(X, y, lr=0.1, epochs=1000, l2=0.0), predict_proba(X) and predict(X, threshold=0.5), trained with batch or mini-batch gradient descent, with a numerically stable sigmoid and log-loss. Then train on a train split, predict on a test split and report accuracy, precision and recall. Handle: a constant feature, a single class in y, separable data. [Reported] [13][15][22][24][56] (phone-screen "traditional ML classifier" [22][24]; "code a ML model from scratch", junior AS [13]; Blind loop summary names LR with gradient descent [15]; Amazon AGI "build/train a small classifier live" [56]; the conceptual loss and MLE were asked in [4]; also a practice prompt [60])

    • Can you derive the gradient of the log loss before you code it?
    • Why log loss and not MSE for this model? What are the model's assumptions? [38]
    • How do you avoid overflow in the sigmoid and log(0) in the loss?
    • Should the bias be regularized? How would you add L1 instead of L2?
    • The classes are 1:100. How do you add class weights to the loss and gradient, and which metric do you report (AUC vs PR-AUC)? [26]
    • How do you show it is learning when you cannot plot?
    • How would you check convergence, and what happens on perfectly separable data?

  3. Gradient descent, then SGD with momentum. Implement gradient_descent(X, y, lr, epochs) -> (w, b) for linear regression with MSE, with the gradient written by hand and vectorized. Then generalize to sgd(params, grad_fn, data, batch_size, lr, momentum, epochs) that shuffles each epoch and applies momentum. Handle: a last batch smaller than batch_size, divergence (loss becomes NaN). [Reported] [19][21][52][70] ("implement gradient descent from scratch", AS intern [19]; "implement SGD for a problem (derive gradients, update, momentum etc.)" [21]; "write and explain gradient descent" [52][70])

    • Why does the learning rate that works for batch GD fail for SGD?
    • What does momentum change about the trajectory on an ill-conditioned problem?
    • Why does feature scaling matter here?
    • How would you add a learning-rate schedule and early stopping?

  4. Ordinary least squares, two ways. Implement fit_ols_closed_form(X, y) with a bias column, and fit_ols_gd(X, y, lr, epochs), and compare their weights on the same data. [Reported] [11][14][27] (Blind: scientist interviewers ask least squares [11][14]; an older review asked for the closed form, when GD is preferable, and the cost of the inversion [27])

    • What is the complexity of the closed form, and when does gradient descent win?
    • When is X^T X singular (collinearity, d > n), and what do you use instead (lstsq, pseudo-inverse, ridge)?
    • Why should you avoid calling np.linalg.inv directly?
    • How would you fit this when X has 1 billion rows and does not fit in memory?

  5. PCA. Implement pca(X: np.ndarray, k: int) -> tuple[components (k, d), projected (n, k), explained_variance_ratio (k,)], with centering and either the covariance eigendecomposition or the SVD. Handle: k > d, n < d, a zero-variance feature. [Reported] [11] (Blind: AS interviewers "tend to ask ML questions such as PCA and least squares")

    • SVD or eigendecomposition: which is more numerically stable, and which is cheaper when d is much larger than n?
    • Why are component signs arbitrary, and how would you make the output deterministic?
    • Should you standardize features first?
    • How would you get only the top component with power iteration?
    • How would you do PCA on data that streams in (incremental PCA)?

  6. Naive Bayes. Implement multinomial Naive Bayes for text: fit(docs: list[list[str]], labels) estimates class priors and per-class word likelihoods with Laplace smoothing; predict(docs) uses log-probabilities. Then do the Gaussian variant for numeric features. Handle: unseen words, a class with no examples of a word, zero variance. [Reported] [53][54] (a Bayesian classifier from scratch, applied to interviewer scenarios, in Amazon Research Scientist and MLE loops; practice prompt [59])

    • Why compute in log space?
    • What does the smoothing parameter do, and how would you pick it?
    • What does the independence assumption break, and when does Naive Bayes still rank well?

  7. Decision tree (CART). Implement DecisionTreeClassifier(max_depth, min_samples_split) with fit(X, y) and predict(X): search every feature and candidate threshold for the best Gini or entropy split, then recurse. Handle: all labels equal, no valid split, duplicate feature values. [Likely] [57] (Amazon-tagged MLE onsite on a practice site, not an AS candidate report; how splits are chosen is asked verbally)

    • What is the cost per node, and how does pre-sorting each feature help?
    • How do you handle categorical features and missing values?
    • How would you store the trained tree as flat arrays for fast prediction?
    • How do you turn it into a random forest, and how do you compute out-of-bag error?

  8. k-nearest neighbors. Implement knn_predict(X_train, y_train, X_query, k) -> labels with fully vectorized pairwise Euclidean distances (no Python loop over n x m pairs), majority vote, and distance-weighted tie-breaking. [Likely] [65]

    • The expansion ||a||^2 - 2ab + ||b||^2 can return small negative values. Why, and how do you fix it?
    • How do you pick k with cross-validation, and why must scaling be fit on training folds only?
    • What is the query cost, and what changes at millions of items (KD-tree, approximate nearest neighbors such as FAISS/HNSW)?

  9. Gradient boosting with stumps. Implement fit_gbm(X, y, n_estimators, learning_rate) that fits depth-1 regression trees to the residuals of squared loss, plus predict. [Likely] (bagging vs boosting asked verbally in AS II loops [6][25]; Blind says boosting is a stretch for live coding [10])

    • What changes for log loss, and what are the pseudo-residuals?
    • How does this differ from bagging in what it does to bias and variance?

  10. Matrix-factorization recommender. Implement train_mf(ratings: list[tuple[user, item, rating]], k, lr, reg, epochs) with SGD on regularized MSE, then predict(u, i) and recommend(u, n) that excludes items the user has already seen. [Likely] [38] (a recommendation-system question followed logistic regression)

    • How do you handle a cold-start user or item?
    • How would you adapt it to implicit feedback (clicks, no ratings)?

  11. Cross-validation and grid search from scratch. Implement stratified_kfold(y, k, seed) and grid_search(model_factory, param_grid, X, y, k) -> (best_params, results) reporting mean and std per config, with preprocessing fit inside each training fold only. [Likely] [22]

    • Where can leakage creep in, and how does your code prevent it?
    • How do you split when rows from the same user must stay together?

  12. L1-regularized regression. Implement lasso(X: np.ndarray (n, d), y: np.ndarray (n,), alpha: float, max_iters: int = 1000, tol: float = 1e-6) -> np.ndarray (d,) with cyclic coordinate descent and soft-thresholding (unpenalized intercept, objective (1/2n)||y - Xw||^2 + alpha ||w||_1). Stop when the max coordinate change is below tol. Handle: an all-zero column, alpha large enough that every weight is zero. [Likely]

    • Why does L1 produce exact zeros and L2 does not?
    • How do you keep the residual updated in O(n) per coordinate instead of recomputing Xw, and how would you compute a warm-started regularization path?

  13. EM for a Gaussian mixture. Implement gmm_em(x: np.ndarray (n,), k: int = 2, max_iters: int = 200, tol: float = 1e-6, seed: int | None = None) -> (means (k,), variances (k,), weights (k,), log_likelihood: float). Compute responsibilities in log space, stop when the log-likelihood gain is below tol, and floor variances at a small epsilon. Handle: a component that collapses onto one point, identical data points. [Likely]

    • How is this related to k-means, and how do you keep the likelihood computation stable?

  14. Linear SVM. Implement fit_linear_svm(X (n, d), y in {-1, +1} (n,), lam: float, epochs: int, batch_size: int, seed) -> (w (d,), b) minimizing lam/2 ||w||^2 + mean(max(0, 1 - y(Xw + b))) by mini-batch subgradient descent with step size 1 / (lam * t) (Pegasos). Handle: labels given as {0, 1}, a batch with no margin violations. [Likely]

    • What does the subgradient do at the margin?

  15. Item-to-item collaborative filtering. Given interactions: scipy.sparse.csr_matrix of shape (n_users, n_items) with implicit counts, implement top_n_similar(interactions, n: int) -> np.ndarray (n_items, n) returning, for each item, the indices of the n most cosine-similar other items (exclude the item itself; items with no interactions return -1 padding). [Likely] (Amazon's item-to-item recommendations)

    • How would you scale this to millions of items without materializing the full similarity matrix?

  3. Beam search decoding. Given next_token_logprobs(prefix: list[int]) -> np.ndarray of shape (V,), a beam width k, max_len and eos_id, implement beam_search(...) -> list[tuple[list[int], float]] returning the top-k finished sequences with cumulative log-probabilities. Stop beams that emit EOS. [Reported] [8] (Santa Clara LLM-team AS screen, 2025; the candidate did not finish working code)

    • When do you stop: all beams finished, or max_len?

    • How does it compare with greedy decoding and with top-k/top-p sampling for an assistant?

  4. Debug a broken Transformer. You are handed a ~100-line PyTorch decoder-only Transformer that trains without errors but whose loss plateaus far above a reference. Find and fix the bugs.     • Which sanity checks would you run (overfit a single batch, compare shapes against a reference, check that loss starts near log V)?

  5. Contrastive loss. Implement a numerically stable, symmetric InfoNCE loss in PyTorch for a batch of paired image and text embeddings (image-to-text and text-to-image), with a temperature. [Reported] [52][53][54] (Research Scientist and MLE loops; sighting Feb 2026)

    • Where does the temperature go, and why use log-sum-exp in both directions?
    • How does batch size change the loss, and why are in-batch negatives a biased sample?

Scope: the ML system design round (also called "Science Application" or "Sys Design (Team-specific)") in the Amazon L5 Applied Scientist (Applied Scientist II) loop, 2024-2026. This chapter contains questions only. It gives no answers or solutions.

How it relates to the older chapters: this chapter merges and dedupes four new search passes (October 2026) with the prompts in amazon-l5-applied-scientist/chapters/06-ml-system-design.md, 12-ml-system-design-reference-diagrams.md and 13-tagging-and-document-understanding-system-design.md. Some Glassdoor review IDs were matched to the right report only approximately (noted in the references). Read each [Reported] tag as "a candidate said this was asked", not as verified fact.

[Likely] means a grounded inference from Amazon job postings, prep guides or the hiring team's products, not seen verbatim in a candidate report. How this round works

  • Where it sits in the loop. Recent AS II loops are a phone screen plus 4-5 onsite interviews of about 55-60 minutes each. Seattle 2026 reports give the loop as "1 Science ML Breadth, 1 Science Depth, 1 Sys Design (Team-specific), 1 coding round and 1 Bar Raiser" [2][3][4]. A Luxembourg loop was a tech talk plus Coding, Science Depth, Science Breadth and Science Application [11]. An August 2024 AS2 loop had 2 phone screens and 5 onsites, one of them a business-problem ML design round [1]. Some recent loops had two practical ML design rounds "related to day to day ml implementations" rather than LeetCode [6][26].
  • What kind of design. This is ML system design, not software architecture. A Berlin candidate found it "higher-level than classic software design", focused on recognizing and applying standard or recent ML approaches [12]. The Alexa round explicitly asked for "ML system design, not software design": datasets, task framing, model choice with justification, and evaluation metrics [1]. Interviewers still ask about latency, scaling, serving, drift monitoring and rollout [22][40].
  • Where the prompt comes from. Usually from the hiring team's own work. A Blind AS2 thread describes the round as taking the team's business problem, framing it as a science problem, and defining data, model, metrics and the learning process [16]. In 2025-2026, GenAI and agentic prompts became common: agentic recommenders, a Copilot-style agent, LLM training and decoding [2][3][9][24][25].
  • Format and tools. Expect a verbal walkthrough on a shared virtual whiteboard or document, with no code to run. The sources do not name a specific tool. The interviewer interrupts with follow-ups after the first end-to-end pass [10]. Plan for about 40 minutes of design and 10-15 minutes of Leadership Principle questions. Amazon interviewers each own one or two LPs, often Customer Obsession, Dive Deep, Invent and Simplify, and Think Big.
  • What the L5 bar is. You must own the whole problem end to end: scope a vague business goal, choose data and labels, justify the model against alternatives, pair offline metrics with an online (Weblab) metric, and plan deployment, monitoring and iteration [16][29]. Depth probes test why you chose each component and whether you know the alternatives. One candidate was down-leveled partly for lacking production experience and for narrowing the problem too much [13]. Breadth questions such as bias-variance and bagging versus boosting can be woven into the design round [2][4].
  • Out of scope here. ML coding (for example ROC AUC from scratch, or a CNN layer forward pass [2][15]) is covered in the ML coding chapter of this focus guide.

1. Design an agentic recommendation system

Prompt. "Design an agentic recommendation system (for example, for Amazon shopping). How would you structure the system, what models or components would you use, and how would you evaluate its quality and safety?" [Reported] [2][3] (Seattle, May-June 2026; the later rounds of that loop focused on agentic product thinking.)

Maps to: Amazon Stores personalization, Rufus, Alexa+ shopping.

 SERVING
 [Shopper msg + context] -> [Intent / planner LLM] -> [Tool router]
                                                       |-> [Catalog search tool]
                                                       |-> [Recs retrieval tool]
                                                       |-> [Cart / order tools]
                            [Ranker / re-ranker] <-----+
                            [Grounding + safety guard] -> [Response + product cards]
 TRAINING / EVAL LOOP
 [Session + tool-call logs] -> [Human + LLM-judge labels] -> [SFT / pref tuning]
 [Offline eval suite: task, safety, red-team] -> [Weblab A/B] -> [Monitoring] -> back

Follow-ups:

  • What does "agentic" add over a standard retrieval-and-ranking recommender? What can the agent do that a ranked carousel cannot?
  • Which decisions belong to the LLM planner, and which stay with classical retrieval and ranking models?
  • How do you define tools (search, filters, compare, add to cart), and how do you stop the agent calling them in loops?
  • How do you ground every recommended product in the live catalog so the agent never invents an ASIN, price or spec?
  • How do you build an offline evaluation set for multi-turn shopping tasks, and what is "task success"?
  • When would you trust an LLM-as-judge for quality, and how do you calibrate it against human raters?
  • Which safety failures matter here (unsafe products, age-restricted items, biased steering, prompt injection from listing text), and how do you red-team them?
  • Which online metrics decide the launch, which are guardrails, and how do you randomize a conversational A/B test?
  • What is your latency budget per turn, and where would you use a small model or a cache instead of the large LLM?
  • How do you personalize using purchase history without breaking privacy expectations?
  • How do sponsored products enter the agent's answers without hurting trust?
  • How do agent recommendations feed back into training data without amplifying the agent's own biases?

25. Cross-cutting probes asked across any prompt

These are not design prompts on their own. They are the probes interviewers attach to whichever prompt you get.

  • Your model improves offline AUC or NDCG but the A/B test shows no lift. What could explain this, and how would you design the experiment (randomization unit, guardrail metrics, sample size, novelty effects)? [Likely] [36][40][51]
  • How would you handle severe class imbalance and label noise, and how would you choose an operating threshold from business costs? [Likely] [28]
  • Explain the bias-variance trade-off and compare bagging with boosting. Which would you use for a tabular fraud or CTR model, and why? [Reported] [2][4]
  • Pick a project on your resume. Why did you choose that model, loss and evaluation over the alternatives? What were the baselines and ablations, what failed, and what would you change to deploy it at Amazon scale? [Reported] [1] (a Senior AS prep thread describes the same probe [27])
  • How would cold start (new users, new items, a new model with no logged history) change the design you just drew? [Likely] [50]
  • What is the proxy label, what is the offline metric versus the business metric, and how will you launch? [Likely] [29]
  • Which parts of your design would you build, and which would you reuse from existing Amazon or AWS services?
  • How would you cut the cost of this system by 50% with minimal quality loss?
  • If you had ten times the data, or one-tenth of it, how would the design change?

Level calibration: harder L5 probes

The bank above leans on component-level follow-ups. These probes test the L5 bar: owning an ambiguous problem end to end, choosing metrics and experiments, and trading model complexity against latency and cost. Attach any of them to any prompt. They are untagged: they are how interviewers typically push past a junior answer, not quoted reports.

  1. Before any model, what one-page problem statement would you write, and which open question would you take back to the product manager first?
  2. Your proxy label and the business metric disagree on the launch decision. Which do you trust, and what evidence would change your mind?
  3. You have p99 headroom for only a model 10x smaller than your best offline model. Where do you spend that budget, and how do you quantify the quality you give up?
  4. Name a design choice you would reverse if serving cost doubled, and one you would keep regardless. Why?
  5. Which metric would you refuse to optimize directly here, even though leadership asks for it, and what would you propose instead?
  6. Your Weblab shows a statistically significant but tiny lift with a guardrail moving the wrong way. Do you launch? Who decides, and on what evidence?
  7. The randomization unit you need is not the one the platform supports (for example, interference across sellers, households or advertisers). How do you still get a trustworthy estimate?
  8. Which slice (new customers, a small marketplace, a long-tail category) could your launch quietly harm, and how would you detect it before the aggregate metric does?
  9. What would you deliberately not build in v1, and how would you defend that cut to a skeptical senior engineer?
  10. Six months after launch, the gain has eroded. How do you separate feedback-loop effects, novelty decay and real drift?
  11. How do you size the team and timeline for v1, and which dependency on another team is the biggest schedule risk?
  12. What offline experiment, run in a week, would most reduce your uncertainty about whether the full system is worth building?

03. Airbnb Senior MLE: ML Coding and Practical Coding

Scope: the coding rounds of the Airbnb Senior (G9) and Senior+ Machine Learning Engineer loop: the technical phone screen, the onsite coding round, the HackerRank-style ML/data screen and the code review round. This chapter contains questions only. It gives no answers or solutions.

How it relates to the older chapters: this chapter merges and dedupes four October 2026 search passes with airbnb-senior-mle/chapters/02-coding-practical.md (practical coding) and 05-ml-fundamentals.md (ML depth). Ch. 02 keeps the long tail of SWE-track problems (banking, refunds, ski DAG, Diplomacy, multi-level online assessments). Ch. 05 keeps verbal ML-theory probes. This chapter keeps the problems most likely to reach an MLE candidate, written as runnable practice prompts.

Source caveat: almost every source is an anonymous candidate self-report (Blind, LeetCode Discuss, Glassdoor, 1point3acres, PracHub) or a prep-vendor page. Many were read only as search-result extracts, and some 1point3acres and PracHub bodies need a login. Several reports come from SWE, data science or data engineering candidates rather than MLEs; the role is noted where it matters. Read [Reported] as "a cited source says this, or a close paraphrase, was asked at Airbnb". [Likely] means a grounded inference from the MLE loop structure, prep guides or Airbnb's published ML work; nobody reported it verbatim.

How this round works

  • Where coding sits in the MLE loop. MLE candidates describe the loop as "LeetCode + standard ML design + an ML experience round" [48][49]. The public MLE-track summary gives one technical phone screen and typically one onsite coding round of 45-60 minutes, and says the track is filtered mainly by design depth [80]. A 2022 senior ML/DS loop instead had two "DS coding" rounds of Airbnb-tagged LeetCode hard and medium problems in Python, plus two ML rounds [47]. A July 2025 ML platform loop had a coding screen and then an onsite with a code review round [53]. Ask your recruiter which mix you will get.
  • Two flavors of coding.   5. Vectorized kNN under a memory cap. 04. Airbnb Senior MLE: Practical ML System Design

Scope. This chapter covers the ML system design rounds in the Airbnb Senior Machine Learning Engineer loop, including the experimentation and A/B testing half of those rounds, for 2024-2026. It lists questions only and gives no answers or solutions.

How it relates to the older chapters. Four new search passes (October 2026) were merged and deduped with the prompts in airbnb-senior-mle/chapters/03-ml-system-design.md, 10-ml-system-design-architecture-diagrams.md and 04-ab-testing-experimentation.md. Those chapters keep the long tail: 140+ search, embedding, pricing and trust sub-questions, full architecture diagrams, and the ERF, CUPED, interleaving and sequential-testing deep dives. This chapter keeps the 24 strongest design prompts. Each one gets a skeleton diagram of the boxes a strong answer must cover. The boxes name components only; they do not say which choice to make.

Source caveat. Almost every source is an anonymous self-report (PracHub [19][20][21], 1point3acres, Blind, or TrueInterview-derived GitHub indexes) or a prep-vendor page. Many were read only as search-result snippets or login-gated teasers. Read each [Reported] tag as "a candidate said this was asked", not as verified fact.

Tag legend:

  • [Reported]: a cited candidate report says the prompt, or a close paraphrase, was asked in an Airbnb MLE loop.
  • [Likely]: a grounded inference from Airbnb papers, the engineering blog, job postings or prep guides. Nobody was seen being asked it verbatim. A citation next to [Likely] points to the system or source that makes it plausible.

Follow-up bullets are untagged unless a source reports them. They are the probes interviewers typically pull on.

How this round works

  • Where it sits in the loop. Expect the design rounds to decide the outcome. Reported loops:
    • An April 2026 Senior MLE loop had four rounds built around ML systems, ranking and marketplace scenarios, with past-project deep dives mixed in. It ended in rejection "on calibration" [2].
    • A September 2026 Senior+ loop (Relevance and Personalization) covered document redaction, project decisions, search ranking without a text query, and retrieval-assisted support. Team matching followed [1].
    • A TrueInterview-derived summary says the loop is "filtered by design depth, not by code", with 1-2 decisive ML design rounds [9].
    • 1point3acres loops had two ML design rounds each: LTV plus host pricing [11]; listing recommendation plus price prediction [12]; property damage claims plus pricing [3].
    • An ML platform loop had a coding screen, then an onsite with code review, one general system design round, one ML system design round and behavioral [7].
  • Two flavors of design round.
    • The ML design round is "typically a search or recommendation question" [6].
    • The ML practitioner round asks you to propose an ML solution to one of Airbnb's real, current engineering problems [6].
    • The ML experience (project) round can turn into an unplanned design question [8][12].
    • Prep guides also list a "debug a model with unexpected behavior" round [22].
  • Duration and tools. Rounds last about 45-60 minutes over video, with a shared doc or whiteboard [9]. You walk through the design verbally; there is no code to run. Interviewers steer partway through, for example from regression to bucketized classification in the LTV round [9].
  • What the senior bar looks like.
    • Drive the problem from business goal to target definition, labels, features, model, offline evaluation, online experiment, serving, and monitoring and debugging in production [1][9].
    • Defend every choice against a simpler and a more complex alternative. Reported probes ask why not a more complex model, how you would trade off precision, recall, latency and infrastructure cost, how you would tune thresholds, and how you would choose between factorization machines and an embedding plus DNN model [2].
    • Show business sense. The April 2026 write-up says "the team really value business sense and decision making" [2].
    • Show two-sided marketplace thinking, covering guests, hosts, supply and demand [6][24].
  • Experimentation weight for this role. Assume every design ends with "how would you launch and measure it?". Prepare for interference-aware randomization (guest, listing, market or two-sided), guardrails, lead-day bias in pricing tests, and what to do when offline and online metrics disagree [2][53][54][56].

1. Search ranking without a text query

Prompt. "Design an ML ranker for Airbnb home search when the user gives no text query, only destination, dates and guest count. Separate the features available at ranking time from future outcomes, set product objectives and guardrails, then pick labels and an architecture. Cover data, evaluation and how you would debug it in production." [Reported] [1][10][13] (Senior+ Relevance and Personalization onsite, September 2026. The broader "design Airbnb search ranking / personalized search ranking" prompt is also reported [6][9][18].)

Maps to: Airbnb stays search ranking, which orders listings by estimated booking probability, evolved from GBDT to deep neural networks [44][45][46]. It also maps to the Relevance and Personalization team [60].

 SERVING
 [Query: dest, dates, guests] -> [Availability + geo filter] -> [Candidate retrieval]
          -> [First-pass ranker] -> [Second-pass ranker] -> [Re-rank: diversity,
             business rules] -> [Results list / map]
 [Feature store: listing | guest | query | real-time session] --> both rankers
 TRAINING LOOP
 [Impression + click + booking logs] -> [Label + position-bias handling]
 -> [Point-in-time feature join] -> [Train] -> [Offline NDCG eval]
 -> [Interleaving / A/B] -> [Monitoring + prod debugging] -> back to logs

Follow-ups:

  • With no query text, what replaces query relevance: location intent, dates, price range, guest history, season?
  • Which features exist at ranking time, and which are future outcomes that would leak into training (eventual booking, later reviews, host cancellation)?
  • What is the primary objective (bookings, booking value, uncancelled stays, long-term guest and host value), and which guardrails protect hosts and marketplace health?
  • Bookings are rare and many searches end without one. Would you train on bookings, clicks, long views, wishlists or contacts to the host? How would you combine them?
  • How do you treat a booking request the host declined or later cancelled?
  • Would you frame the model as pointwise, pairwise or listwise, and how do you build training pairs from a session with one booked listing?
  • How do you correct for position bias in logged results, and what position value do you feed at inference time?
  • How do you give cold-start listings controlled exposure without hurting conversion?
  • When does moving from a GBDT to a neural ranker pay off, and what usually breaks (feature scaling, sparse IDs, price sensitivity)?
  • What is the latency budget for each stage, and which features are batch versus real-time?
  • How would ranking change for the map view, for Experiences, or for long-term stays? [Likely] [29][47]

2. Pricing prediction and Smart Pricing

Prompt. "Design a pricing prediction / price recommendation (Smart Pricing) model for Airbnb hosts. Cover the features (listing, seasonality, demand, comparable listings), the label when you only observe booked prices, and how you evaluate it." [Reported] [3][4][5][11][12] (1point3acres onsites 2022-2025: "ML round 1: a price prediction system" [5]; "design a system to help hosts set prices" [11]; "price prediction" [12]. Prep guides also list "dynamic pricing recommendation engine" [22][25][26].)

Maps to: Airbnb dynamic pricing (Smart Pricing), which combines a booking-probability model with a customized price regression [51]. It also maps to the host calendar's comparable-listing embeddings [42].

 SERVING
 [Listing + night + lead time] -> [Demand / booking-prob model] -> [Price strategy
          model] -> [Host constraints: min/max, rules] -> [Suggested price + reason]
 [Comps: similar listings] [Seasonality + events] [Market supply/demand] --> models
 TRAINING LOOP
 [Calendar + price + booking logs] -> [Label: booked / unbooked nights, censoring]
 -> [Train] -> [Offline eval: price regret, calibration] -> [Host adoption logs]
 -> [Pricing A/B with lead-day handling] -> [Monitoring] -> back to logs

Follow-ups:

  • What exactly are you predicting: the market-clearing price, booking probability at a given price, or the host's revenue-maximizing price?
  • You only see the price for booked nights and the host's asking price for unbooked ones. How do you build a label from that censored, host-chosen data?
  • Observed prices are set by hosts, not randomized. How do you separate the price effect from listing quality (endogeneity)?
  • What feature families matter (listing attributes, location, seasonality, local events, lead time, comps, market occupancy)?
  • How do you pick comparable listings, and could listing embeddings do it better than hand-built rules?
  • What offline metric fits when the "right price" is never observed?
  • How do you respect host goals (occupancy versus nightly rate) and host-set minimums?
  • How do you explain a suggestion so that hosts adopt it?
  • Many hosts in one market adopt the suggestion. How do you account for that feedback loop?
  • Would you randomize a pricing test by listing, by night or by market? Why does lead-day bias matter? [Likely] [56]
  • How would you replace a rule-based pricing function (weekend, event and competitor bounds) with ML, and how would you prove it is better? [Likely] [27]
  • How does the system behave for a brand-new listing with no booking history?
  • How would damage or cancellation risk enter pricing or security-deposit decisions? (One reported loop paired a pricing round with a damage-claims round.) [Likely] [3]

3. Retrieval-assisted (RAG) customer support

Prompt. "Design a retrieval-assisted customer support system for Airbnb guests and hosts that answers questions or helps agents. Cover knowledge-base retrieval, LLM generation, evaluation, guardrails and escalation to humans." [Reported] [1][9][17] (Senior+ onsite, September 2026 [1]. 2026 senior loops added retrieval and ranking prompts for GenAI support tools [9]. A related prompt is "generate customer-support instructions from company policies" [17].)

Maps to: Airbnb Community Support chat and voice AI assistants. The team's postings list SFT, RL, distillation, RAG/search, LLM evaluation, feedback-based learning and guardrails [62][64][65]. An October 2025 paper covers LLMs in Airbnb support [67], and an earlier case study covers support text generation [68].

 SERVING
 [Guest/host message + reservation ctx] -> [Intent + risk classifier]
   -> [Retriever: help center, policies, past cases] -> [Re-ranker]
   -> [LLM generator (distilled)] -> [Guardrails: policy, PII, safety]
   -> [Answer | agent suggestion | escalate to human]
 TRAINING / EVAL LOOP
 [Tickets + resolutions + CSAT] -> [Human + LLM-judge labels] -> [SFT / pref tuning]
 -> [Offline eval: groundedness, resolution] -> [A/B] -> [Feedback logs] -> back

Follow-ups:

  • Which intents should the bot answer itself, which should it draft for an agent, and which must go straight to a human (safety, emergencies, high-value refunds)?
  • How do you chunk and index help-center and policy content that changes often and differs by country?
  • How do you retrieve reservation-specific context (dates, cancellation policy, payment status) safely?
  • Would you use RAG, SFT or both? When does distilling into a smaller model pay off on latency and cost?
  • How do you build an offline evaluation set, and which metrics matter (groundedness, policy correctness, resolution, tone)?
  • When can you trust an LLM-as-judge, and how do you calibrate it against human reviewers?
  • Which guardrails stop the model promising refunds or exceptions that policy does not allow?
  • How do you detect and hand off escalations without losing context?
  • Which online metrics decide the launch (resolution rate, contact rate, CSAT, handle time), and would you randomize by ticket, by user or by agent?
  • How do you learn from agent edits and user feedback without amplifying the model's own mistakes?
  • How do you protect against prompt injection from user messages or listing text?
  • What is the per-turn latency budget for chat versus voice?

4. User embeddings and two-stage semantic retrieval and ranking

Prompt. "Design a user embedding plus two-stage semantic retrieval and ranking system for Airbnb search, optimized for booking conversion. Walk through candidate generation, the ranker, features, labels and online serving." [Reported] [2][10][14] (April 2026 Senior MLE onsite [2]. "Design user-embedding semantic search", reported April 2026 [10][14].)

Maps to: Airbnb embedding-based retrieval (a two-tower model with listing embeddings precomputed daily, targeted negative sampling, IVF chosen over HNSW, and traffic-replay evaluation) [39][40][41]. It also maps to user-type embeddings [43] and BiListing multimodal listing vectors [52].

 SERVING
 [Guest ctx + query] -> [User / query tower] -> [ANN index (listing tower,
     precomputed)] + [Availability / geo / price filters] -> [Top-K candidates]
   -> [Ranker (booking objective)] -> [Results]
 [Batch: listing embeddings daily] [Stream: session events -> user embedding]
 TRAINING LOOP
 [Search sessions + bookings] -> [Positives + negative sampling] -> [Two-tower train]
 -> [Offline recall@K, traffic replay] -> [Index rebuild] -> [A/B] -> back

Follow-ups:

  • How do you build a user embedding from sparse, long-gap travel histories, and how do you refresh it in-session?
  • What counts as a positive (booked, wishlisted, long view), and which negatives do you sample (in-batch, same-market, hard negatives)?
  • Why might random negatives produce embeddings that mostly learn geography?
  • Price and availability change daily. What stays inside the embedding, and what goes into filters at query time?
  • When would you pick IVF over HNSW, given index rebuild cost and frequent filtering?
  • How do you evaluate retrieval recall separately from end-to-end ranking quality, when inventory changes every day?
  • How do you share the latency budget between retrieval and ranking? Each stage scores about an order of magnitude fewer homes than the one before [40].
  • How do you represent a new guest or a new listing in the embedding space?
  • How do you keep retrieval from narrowing what the ranker can ever learn from (a feedback loop)?
  • How would you fold photo and text embeddings into one listing vector, and how would you measure the NDCG and revenue impact? [Likely] [52]
  • What do you A/B test first, retrieval or ranker, and how do you attribute the gain?

5. Offline wins, online flat: diagnose and decide

Prompt. "Your new ranking model wins on offline metrics such as NDCG/AUC but is flat or negative in the online A/B test. How do you diagnose the gap, and what do you ship?" [Reported] [2] (April 2026 Senior MLE: "What do you do when the offline metric and the online metric disagree?". A related prompt, "debug a model with unexpected behavior", appears in prep guides [22], and the Senior+ report advises preparing production debugging [1].)

Maps to: Airbnb's deep-learning search papers, which describe many offline wins that failed online [44][45], plus interleaving for faster ranking tests [58].

 [Offline eval set] --vs-- [Online A/B readout]
        |                          |
 [Label / objective check]  [Experiment health: SRM, exposure, power, novelty]
 [Leakage + split check]    [Interference between arms]
 [Candidate-set mismatch]   [Segment / market breakdown]
        \                         /
       [Training-serving skew: feature parity + latency]
                    |
         [Decision: ship / iterate / kill] -> [Post-launch monitoring]

Follow-ups:

  • What is your first check, the experiment or the model?
  • How do you test for training-serving skew, feature leakage and stale features?
  • Was the offline candidate set the same as what the online ranker actually scored?
  • Could position bias or a feedback loop (training on control's rankings) explain the gap?
  • Does the offline metric measure the online objective (bookings versus clicks, uncancelled stays)?
  • Did the new model add latency, and how would you separate the latency effect from the quality effect?
  • Could interference between arms or novelty effects hide a real gain?
  • Which segments or markets moved in opposite directions?
  • Would interleaving have given a faster or clearer read? [Likely] [58]
  • The result is +0.3% bookings with a wide interval, plus extra latency and infrastructure cost. Do you ship? [Likely]
  • How would you build an offline metric that predicts online wins better next time?
  • Conversion drops in one market the day after a new ranker ships. Walk through rollback criteria and root-cause analysis (data, features, serving skew, model). [Likely] [1][22]
  • The interviewer pushes back on your launch call. How do you defend it on business grounds? [Reported] [2]

Prompt. "Design a system to calculate customer (or listing) lifetime value." [Reported] [9][10][11][15] (1point3acres loop [11]; listing LTV reported May 2026 [10][15].)

Maps to: Airbnb's future-value measurement, used to standardize trade-offs across teams (see the older chapter airbnb-senior-mle/chapters/03-ml-system-design.md).

 SERVING
 [Guest / listing entity] -> [Feature snapshot at time t] -> [LTV model]
   -> [Calibrated value or value bucket] -> [Consumers: marketing, ranking,
      host acquisition, incentives]
 TRAINING LOOP
 [Booking + revenue + churn history] -> [Target definition: horizon, margin]

Follow-ups:

  • How do you define LTV: revenue or contribution margin, over what horizon, and for which entity?
  • How do you handle right-censoring for recent users and listings?
  • Why might bucketized classification beat regression on a heavy-tailed target?
  • How do you predict LTV for brand-new guests or listings?
  • Which features are allowed without leaking future behavior?
  • How do you evaluate it: calibration by decile, rank correlation, or business backtests?
  • Who consumes the score, and how would each consumer misuse it?
  • How would you validate that decisions based on LTV (incentives, host acquisition spend) actually raise long-term value?
  • How often do you retrain, and how do you detect drift after a macro shock (for example, a travel slowdown)?

[Reported] [9][19][20] (PracHub-listed Airbnb prompt [19][20]; cover-photo and high-quality-listing prompts in a 2026 summary [9].)

 SERVING
 [Listing photos + text + amenities] -> [Image encoder] + [Text encoder]
   -> [Quality model / cover-photo selector] -> [Quality score + reasons]
   -> [Consumers: search ranking feature, host tips, merchandising]

Follow-ups:

  • What does "quality" mean: photo aesthetics, accuracy versus reality, completeness, or predicted guest satisfaction?

  • How do you keep the model from learning that "expensive-looking" equals "high quality"?
  • How do you pick the cover photo per listing, and could it be personalized per guest?
  • How would the score enter search: as a ranker feature, as a filter, or as a boost? What feedback loop does that create?
  • How would you measure the model's effect on hosts (photo uploads, edits) as well as guests?
  • How do you handle new listings with few photos, or photos that are not of the home?

  • How do you audit quality scores for bias against particular regions or property types?

   -> [Classifier] -> [Calibrated prob] -> [Threshold] -> [Tag / filter in search]

10. Threshold choice and model choice under cost constraints

Prompt.             |

16. Two-sided marketplace A/B test for a ranking or pricing launch

Prompt. "You launch a new ranking or pricing model. How do you design the A/B test in Airbnb's two-sided marketplace, where treatment and control compete for the same inventory? Would you randomize by guest, by listing or by market, and when is each design unbiased?" [Likely] [33][34][53][54] (Experiment-design prompts appear in the Airbnb question index [10] and an Airbnb data-science prep guide [37], role unspecified. Interference is a core topic in Airbnb-coauthored research [53].)

Maps to: Johari, Li, Liskovich and Weintraub (Stanford and Airbnb): customer randomization is unbiased in demand-constrained markets, listing randomization in supply-constrained ones, and two-sided randomization (TSR) is proposed [53]. Holtz and Aral show that ignoring interference can inflate estimates by up to 100% [54]. Airbnb's own experimentation write-ups cover the platform side [59].

 [Hypothesis + primary metric + guardrails (guest AND host)]
      -> [Randomization unit: guest | listing | two-sided | market cluster]
      -> [Power calc with clustering] -> [Assignment + exposure logging]
      -> [Run: novelty window, SRM checks]
      -> [Analysis: variance reduction, interference diagnostics, segments]
      -> [Launch decision] -> [Holdout / long-term readout]

Follow-ups:

  • How does interference bias a guest-randomized test when inventory is limited?
  • When would you randomize listings instead, and what bias does that leave?
  • How does two-sided randomization work, and what bias-variance trade-off remains?
  • When is market-level or cluster randomization worth the loss in power?
  • How do you compute power when randomizing clustered units?
  • Which guest metrics and which host metrics do you track as primary and guardrail?
  • A new search filter raised bookings but lowered host response rates. Would you launch? [Likely] [34]
  • How would you detect novelty effects in a ranking test?
  • How would you measure cannibalization of a new category, with holdout regions or synthetic controls? [Likely] [34]
  • Which pitfalls (peeking, dilution, marketplace-level bias) should the platform guard against automatically? [Likely] [57]
  • Walk through the experiment from hypothesis to launch call. [Likely] [38]
